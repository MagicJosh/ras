## 1. What do independent sources say about multi-agent versus single-agent performance, cost, latency and failure modes?

### Takeaway
Independent sources agree on a narrow rule: multiple agents pay off for read-only, parallelizable, breadth-first work that would overflow one context window, and they hurt for sequential or tightly coupled work, where a single agent with the full context is better. The cost is more model calls and tokens, and every source that gives design advice says to default to one agent and split only on a clear reason.

**Cognition (not opened)**
- [search summary] Walden Yan, "Don't Build Multi-Agents" (2025-06-12). Two principles: (1) share context, including full agent traces and not only individual messages; (2) actions carry implicit decisions, and conflicting decisions produce bad results. Yan says architectures that break these should be ruled out by default. Example: a Flappy Bird clone split into a background subtask and a bird subtask comes back in mismatched styles, and copying the original task into each subagent does not fully fix it. — [Cognition blog](https://cognition.ai/blog/dont-build-multi-agents)
- [search summary] Walden Yan, "Multi-Agents: What's Actually Working" (2026-04-22), a refinement and not a reversal: a narrower class works "where agents contribute intelligence while writes stay single-threaded"; parallel-writer swarms still see little adoption; a review loop worked best when the reviewer started from a clean context and not the coder's accumulated reasoning. — [Cognition blog](https://cognition.com/blog/multi-agents-working)

### Inferences
- The independent evidence converges on a task test, not a blanket verdict. Three questions decide it: is the work read-only, are the subtopics independent, and would the raw material overflow or pollute one context? Three yes answers favor lead-plus-researchers; any no favors one agent.
- A small research feature whose questions are often narrow (one library, one error, one design choice) sits mostly on the single-agent side. Open Deep Research's own rule ("single sub-agent" for fact-finding, one per element only for explicit comparisons) is a ready-made dispatch rule.
- Research is the favorable case for multiple agents under Cognition's own criteria, because researchers only read and the lead is the only writer. Cognition's 2026 follow-up says the same in general terms.
- The scaling study's "45% single-agent baseline" and error-amplification numbers point the same way as the vendor advice: when one capable agent already does well, adding agents mostly adds cost and error surface. This is an inference from secondary summaries, not from the paper's own tables.
- The LangChain token example cuts both ways. Subagents used fewer tokens than a single agent that loads everything (9K versus 15K), but more calls than a single agent on a simple request (4 versus 3). Isolation saves tokens only when there is a lot of domain context to keep apart.

## 2. What failure taxonomies exist for multi-agent LLM systems, and which failures apply to a lead-plus-researchers setup?

### Takeaway
MAST (Cemri et al., UC Berkeley, NeurIPS 2025) is the reference taxonomy: 14 failure modes in three groups (specification or system design, inter-agent misalignment, task verification), built from annotated traces of seven frameworks. The mode definitions are read from the repository. Three percentage breakdowns are in circulation: 37.17 / 31.41 / 31.41 in the repository figure (the only set I opened; the figure's commit is labelled "arxiv v1", March 2025) and two other sets in secondary sources, possibly from other paper versions. All three agree that the specification or design group is the largest and that verification is never the largest.

### Cited Findings
- [opened] The MAST repository describes the paper as "the first comprehensive study of MAS challenges: MAST (Multi-Agent Systems Failure Taxonomy)" and releases a "dataset with over 1K annotated MAS traces", with both LLM-judge and human labels. — [MAST README](https://github.com/multi-agent-systems-failure-taxonomy/MAST/blob/main/README.md)
- [opened] The 14 modes, with names exactly as in the repository's definitions file — [MAST definitions.txt](https://github.com/multi-agent-systems-failure-taxonomy/MAST/blob/main/taxonomy_definitions_examples/definitions.txt):
  - Group 1: 1.1 Disobey Task Specification; 1.2 Disobey Role Specification; 1.3 Step Repetition; 1.4 Loss of Conversation History; 1.5 Unaware of Termination Conditions.
  - Group 2: 2.1 Conversation Reset; 2.2 Fail to Ask for Clarification; 2.3 Task Derailment; 2.4 Information Withholding; 2.5 Ignored Other Agent's Input; 2.6 Action-Reasoning Mismatch.
  - Group 3: 3.1 Premature Termination; 3.2 Weak Verification; 3.3 No or Incorrect Verification.
  - The definitions file gives no group names; the group names below come from the repository's figure.
- [opened] The taxonomy figure in the repository (file `taxonomy_v11_cropped-1.png`, embedded in a README that links version 2 of the paper) names the groups and prints a share for every mode — [MAST taxonomy figure](https://github.com/multi-agent-systems-failure-taxonomy/MAST/blob/main/assets/taxonomy_v11_cropped-1.png):
  - "Poor Specification (System Design)" 37.17%: 1.1 Disobey Task Specification 15.2%; 1.2 Disobey Role Specification 1.57%; 1.3 Step Repetition 11.5%; 1.4 Loss of Conversation History 2.36%; 1.5 Unaware of Termination Conditions 6.54%.
  - "Inter-Agent Misalignment (Agent Coordination)" 31.41%: 2.1 Conversation Reset 5.50%; 2.2 Fail to Ask for Clarification 2.09%; 2.3 Task Derailment 5.50%; 2.4 Information Withholding 6.02%; 2.5 Ignored Other Agent's Input 4.71%; 2.6 Reasoning-Action Mismatch 7.59%.
  - "Task Verification (Quality Control)" 31.41%: 3.1 Premature Termination 8.64%; 3.2 No or Incomplete Verification 9.16%; 3.3 Incorrect Verification 13.61%.
  - The figure was committed on 2025-03-16 with the commit message "arxiv v1" and has not changed since, so these shares are most likely the first arXiv version's breakdown; the definitions file was added on 2025-04-14 (dates from the repository's git history).
  - The per-mode shares add up to the three group totals. The figure also places each mode on a timeline of "Pre Execution", "Execution" and "Post Execution" stages.
  - Naming differs inside the repository: the figure calls 3.2 "No or Incomplete Verification" and 3.3 "Incorrect Verification", while the definitions file calls them "Weak Verification" and "No or Incorrect Verification"; 2.6 is "Reasoning-Action Mismatch" in the figure and "Action-Reasoning Mismatch" in the definitions file.
- [opened] 1.1: failure "to adhere to specified constraints, guidelines, or requirements associated with a particular task. Non-compliance can result from unclear, incomplete, or ambiguous instructions provided by the user, system prompts, or task descriptions." — [MAST definitions.txt](https://github.com/multi-agent-systems-failure-taxonomy/MAST/blob/main/taxonomy_definitions_examples/definitions.txt)
- [opened] 1.3: an agent "unnecessarily repeats a phase, a task, a stage that have already been completed. Such redundancy can arise from inadequate state or context tracking". — [MAST definitions.txt](https://github.com/multi-agent-systems-failure-taxonomy/MAST/blob/main/taxonomy_definitions_examples/definitions.txt)
- [opened] 1.5: failure "to adhere to criteria designed to trigger the termination of an interaction", caused by "ambiguous, incomplete, or poorly defined stopping conditions". — [MAST definitions.txt](https://github.com/multi-agent-systems-failure-taxonomy/MAST/blob/main/taxonomy_definitions_examples/definitions.txt)
- [opened] 2.2: "Inability to request additional information between agent when faced with unclear or incomplete data, potentially resulting in incorrect actions." — [MAST definitions.txt](https://github.com/multi-agent-systems-failure-taxonomy/MAST/blob/main/taxonomy_definitions_examples/definitions.txt)
- [opened] 2.4: an agent "possesses critical information but fails to share it promptly or effectively with other agents or system components that rely upon this information". Consequences include "unnecessary redundant processing, incorrect or suboptimal decision-making", and "initial failures due to withheld information can trigger cascading errors". — [MAST definitions.txt](https://github.com/multi-agent-systems-failure-taxonomy/MAST/blob/main/taxonomy_definitions_examples/definitions.txt)
- [opened] 2.5: "Not properly considering input or recommendations provided by other agents in the system". — [MAST definitions.txt](https://github.com/multi-agent-systems-failure-taxonomy/MAST/blob/main/taxonomy_definitions_examples/definitions.txt)
- [opened] 3.1: "Ending a dialogue, interaction or task before all necessary information has been exchanged or objectives have been met", including information agents "already obtained but failed to communicate to other agents before termination." — [MAST definitions.txt](https://github.com/multi-agent-systems-failure-taxonomy/MAST/blob/main/taxonomy_definitions_examples/definitions.txt)
- [opened] 3.2 and 3.3: verification that exists but is "incomplete, superficial, or insufficiently rigorous", or "Omission of proper checking or confirmation of task outcomes or system outputs, potentially allowing errors or inconsistencies to propagate undetected." — [MAST definitions.txt](https://github.com/multi-agent-systems-failure-taxonomy/MAST/blob/main/taxonomy_definitions_examples/definitions.txt)

- [search summary] Secondary sources quote two other sets of category shares, and neither matches the repository figure (37.17% / 31.41% / 31.41%): about 41.8% / 36.9% / 21.3% (specification / misalignment / verification) from secondary sources the search did not name, and 44.2% / 32.3% / 23.5% from two blog posts. The paper has several versions with different trace counts, which may explain the three sets; I could not check the paper's own tables. — [syntrox summary](https://www.syntrox.io/blog/why-multi-agent-systems-fail); [rerun.build summary](https://rerun.build/blog/why-multi-agent-llm-systems-fail)

- [opened] Framework docs name one failure that is specific to the subagent pattern: "A common failure mode is that the sub-agent performs tool calls or reasoning but doesn't include results in its final message—remind it that the supervisor only sees the final output." — [LangChain docs, multi-agent/subagents.mdx](https://github.com/langchain-ai/docs/blob/main/src/oss/langchain/multi-agent/subagents.mdx)
- [opened] Google ADK names a concurrency failure for parallel branches that share state: "Because the branches run concurrently, do not rely on one branch reading a key another branch is still writing." — [adk-docs parallel-agents.md](https://github.com/google/adk-docs/blob/main/docs/agents/workflow-agents/parallel-agents.md)

### Inferences
Mapping of MAST modes to a lead that spawns read-only researchers and then synthesizes. This mapping is my own, not from the paper.

| MAST mode | Applies to lead-plus-researchers? | How it shows up |
|---|---|---|
| 1.1 Disobey Task Specification | Yes, high | The delegation brief is the only thing a researcher sees, so a vague brief gives off-scope or wrong-format notes. |
| 1.3 Step Repetition | Yes | Two researchers run the same searches because scopes overlap; the lead re-researches what a researcher already covered. |
| 1.5 Unaware of Termination Conditions | Yes | Researchers keep searching with no stop rule; the lead keeps delegating "for perfection". Open Deep Research counters this with explicit tool-call limits. |
| 2.2 Fail to Ask for Clarification | Yes, structural | A one-shot subagent normally cannot ask the lead a question, so it guesses. |
| 2.4 Information Withholding | Yes, high | The researcher found a caveat, a conflicting source or a dead end, and left it out of its final message. This is the handoff-loss failure. |
| 2.5 Ignored Other Agent's Input | Yes | The lead drops or flattens a researcher's caveat or gap when it synthesizes. |
| 3.1 Premature Termination | Yes | A researcher returns after one source; the lead synthesizes before all researchers report. |
| 3.2 / 3.3 Weak or no verification | Yes, high | The lead treats researcher claims as verified facts with no check of the source. |
| 2.3 Task Derailment | Partly | A researcher drifts into an adjacent topic. |
| 1.2 Disobey Role Specification | Low | Only if a researcher starts editing files or writing the final report; tool restrictions remove most of it. |
| 1.4 Loss of Conversation History, 2.1 Conversation Reset | Low | These fit long multi-turn agent dialogues; a one-shot researcher has little history to lose. Compaction inside a long researcher run is the remaining case. |
| 2.6 Action-Reasoning Mismatch | Partly | A researcher's stated conclusion does not match what its sources said. |

- Several of the applicable modes (1.1, 1.5, 2.4, 3.1, 3.2/3.3) are addressed by the handoff format itself: a brief with scope and stop rule on the way down, and a fixed return template with sources, gaps and confidence on the way up.

### Gaps
- The paper's own tables, the list of the seven frameworks and the per-framework results were not verified, because arxiv.org, the Berkeley project page (sites.google.com) and the Hugging Face dataset card were all unreachable. The only verified percentages are those printed in the repository figure, and I could not confirm which paper version and trace count that figure reflects.
- Three different category breakdowns are in circulation (figure: 37.17 / 31.41 / 31.41; blogs: 41.8 / 36.9 / 21.3 and 44.2 / 32.3 / 23.5). A report should cite one with its version, or say only that the three groups are of the same order of magnitude.
- The 41.8 / 36.9 / 21.3 set has no named source: a query that contained those numbers returned no confirmation, and a later query returned the set without saying where it came from.
- I found no taxonomy written specifically for research (lead-plus-researchers) systems. MAST's traces are dominated by coding and general task frameworks (stated in secondary summaries only).

## 3. What is recommended for passing results between agents, and what is reported about detail lost in summaries?

### Takeaway
Frameworks converge on four mechanisms: the receiver sees only the sender's final message unless told otherwise; a declared output schema turns that message into validated data; files or shared state hold the full record while only a pointer or short summary enters context; and automatic compaction is a last resort that keeps the original on disk. On loss, the engineering sources treat summarization as lossy by design and guard against it with "do not summarize, preserve sources" instructions; measured studies of handoff loss exist only as 2026 preprints I could not open.

### Cited Findings

**Only the final message crosses the boundary**
- [opened] LangChain subagents: "the task description is passed as a human message to the sub-agent, and the sub-agent's final message is returned as the tool result." Two fixes for bad returns: "Prompt the sub-agent: Specify exactly what should be returned" and "Format in code: Adjust or enrich the response before returning it. For example, pass specific state keys back in addition to the final text". — [LangChain docs, multi-agent/subagents.mdx](https://github.com/langchain-ai/docs/blob/main/src/oss/langchain/multi-agent/subagents.mdx)
- [opened] Deep Agents has a best-practice heading "Return concise results": "Instruct subagents to return summaries, not raw data". — [LangChain docs, deepagents/subagents.mdx](https://github.com/langchain-ai/docs/blob/main/src/oss/deepagents/subagents.mdx)

**Structured output schemas**
- [opened] Deep Agents `response_format`: "When set, the parent receives the subagent's result as JSON instead of free-form text. Accepts Pydantic models, `ToolStrategy(...)`, `ProviderStrategy(...)`, or a raw schema type." — [LangChain docs, deepagents/subagents.mdx](https://github.com/langchain-ai/docs/blob/main/src/oss/deepagents/subagents.mdx)
- [opened] OpenAI Agents SDK recommends "Using structured outputs to generate well formed data that you can inspect with your code" for code-driven orchestration. For handoffs, `input_type` is a schema for small model-generated metadata: "Use `input_type` when the handoff needs a small piece of model-generated metadata such as `reason`, `language`, `priority`, or `summary`." — [openai-agents-python docs/multi_agent.md](https://github.com/openai/openai-agents-python/blob/main/docs/multi_agent.md); [docs/handoffs.md](https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md)
- [opened] Claude Code dynamic workflows: "If you pass a `schema` on an `agent()` call, that subagent returns JSON matching the shape instead of prose." Output that fails validation is retried; "If the subagent's output still fails validation after five attempts, the call fails". — [Claude Code docs, workflows](https://code.claude.com/docs/en/workflows.md)
- [opened] Magentic-One forces the orchestrator's progress ledger into a fixed JSON schema: "DO NOT OUTPUT ANYTHING OTHER THAN JSON, AND DO NOT DEVIATE FROM THIS SCHEMA". Every field pairs an `answer` with a `reason`. — [autogen _magentic_one/_prompts.py](https://github.com/microsoft/autogen/blob/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_prompts.py)

**Full transcript versus summary on a handoff**
- [opened] OpenAI Agents SDK default is the full transcript: "When a handoff occurs, it's as though the new agent takes over the conversation, and gets to see the entire previous conversation history." An `input_filter` can change that; a built-in filter `remove_all_tools` strips tool items. — [openai-agents-python docs/handoffs.md](https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md)
- [opened] Summarized handoff history is "an opt-in beta and is disabled by default while we stabilize it". When enabled, "the runner compacts summarizable history into ordered assistant summary segments while preserving lossless message items in their original positions." — [openai-agents-python docs/handoffs.md](https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md)
- [search summary] Cognition's first principle is the opposite of a summary-only handoff: share full agent traces, not just individual messages, because a delegated subtask depends on decisions the main agent already made. — [Cognition blog](https://cognition.ai/blog/dont-build-multi-agents)

**Files and shared state**
- [opened] Google ADK: a parallel agent "does not gather the results into a list you can read afterwards... To use a sub-agent's result, read it from the shared session state, for example the key it was given through `output_key`." Advice: "give each sub-agent an `output_key` and read those keys from a later agent's instruction." — [adk-docs parallel-agents.md](https://github.com/google/adk-docs/blob/main/docs/agents/workflow-agents/parallel-agents.md)
- [opened] Deep Agents offloading: "Large tool inputs and results are stored in the filesystem and replaced with references." When a tool result exceeds 20,000 tokens, "the deep agent offloads the response to the configured backend and substitutes it with a file path reference and a preview of the first 10 lines. Agents can then re-read or search the content as needed." — [LangChain docs, deepagents/context-engineering.mdx](https://github.com/langchain-ai/docs/blob/main/src/oss/deepagents/context-engineering.mdx)
- [opened] Claude Code dynamic workflows keep intermediate results out of the lead's context entirely: "A workflow script holds the loop, the branching, and the intermediate results itself, so Claude's context holds only the final answer." — [Claude Code docs, workflows](https://code.claude.com/docs/en/workflows.md)
- [opened] Open Deep Research keeps two channels per researcher in its state schema: `compressed_research` (the cleaned findings that go to the supervisor) and `raw_notes` (the unprocessed record), and both are carried up to the top-level state as `notes` and `raw_notes`. — [open_deep_research state.py](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/state.py)

**Compaction and what is known about loss**
- [opened] Deep Agents summarization triggers at 85% of the model's input window, keeps 10% of tokens as recent context, and is paired with a full record on disk: "An LLM generates a structured summary of the conversation including session intent, artifacts created, and next steps" and "A text rendering of the original conversation messages is written to the filesystem as a canonical record." The stated reason: "preserving the ability to recover text details when needed (via filesystem search)." — [LangChain docs, deepagents/context-engineering.mdx](https://github.com/langchain-ai/docs/blob/main/src/oss/deepagents/context-engineering.mdx)
- [opened] A fork inherits loss that already happened: "If the parent has compacted its history, the fork receives that compacted context, not every original message." — [LangChain docs, deepagents/subagents.mdx](https://github.com/langchain-ai/docs/blob/main/src/oss/deepagents/subagents.mdx)
- [opened] Open Deep Research's researcher-to-supervisor step is written to prevent loss, not to shorten. From its compression prompt: "All relevant information should be repeated and rewritten verbatim, but in a cleaner format."; "it's crucial that you don't lose any information from the raw messages"; "It's really important not to lose any sources. A later LLM will be used to merge this report with others, so having all of the sources is critical."; and the human message "DO NOT summarize the information. I want the raw information returned, just in a cleaner format." — [open_deep_research prompts.py](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/prompts.py)
- [opened] Google ADK presents compaction as a cost tool: summarizing older history "optimizes latency and reduces costs", with `event_retention_size` recent events kept "in 'raw' un-compacted format". — [adk-docs compaction.md](https://github.com/google/adk-docs/blob/main/docs/context/compaction.md)
- [opened] A privacy side effect of summarized handoffs: "Tool-call arguments and tool outputs can remain in the generated assistant summary even when the corresponding structured tool items are no longer forwarded separately." — [openai-agents-python docs/handoffs.md](https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md)
- [search summary] 2026 preprints on compaction loss: Slipstream (arXiv 2605.08580) says that once a summary replaces the original context the agent cannot independently check the handoff; "Parallel Context Compaction" (arXiv 2605.23296) says summarization is inherently lossy and that summary length and content become unstable at longer contexts; "Toward Reliable Context Compression for Long-Horizon Agents" (arXiv 2608.06503) finds agents conditioned on a summary perform worse on tasks, attributed to omitted information, distorted progress or poor use of what was kept; KVMem (arXiv 2609.04852) notes a summary may omit low-salience evidence that later becomes essential. — [arXiv 2605.08580](https://arxiv.org/pdf/2605.08580); [arXiv 2605.23296](https://arxiv.org/pdf/2605.23296); [arXiv 2608.06503](https://arxiv.org/pdf/2608.06503); [arXiv 2609.04852](https://arxiv.org/pdf/2609.04852)

### Inferences
- The safest pattern for research handoffs, supported by three independent implementations (Open Deep Research, Deep Agents, ADK), is two channels: a full notes file as the durable record, and a short return message that points to it. The lead reads the file only when it needs detail. This removes the choice between "concise summary" and "nothing lost".
- "Summary" in vendor docs means two different things. Deep Agents and Claude Code mean a short digest to protect the lead's context. Open Deep Research means a cleaned, de-duplicated, complete record. A research feature that feeds a planning step needs the second for the notes file and the first for the return message.
- Loss of low-salience detail (caveats, ruled-out options, conflicting sources) is the specific risk. A template that has explicit slots for gaps, conflicts and dead ends makes omission visible, because an empty slot is noticeable where a missing sentence is not.
- Schemas guard format, not truth. A schema-valid return can still drop a caveat or invent a source; verification is a separate step (MAST group 3).

### Gaps
- No opened source reports a measured loss rate for subagent-to-lead summaries. The four preprints above were found only as search summaries and study in-session compaction, not handoffs between agents.
- A search result attributed a "telephone game" description of handoff loss to Anthropic; I could not confirm the attribution and Anthropic's multi-agent post is out of scope for this pass.
- OpenAI's handoff prompt-prefix recommendation and Cognition's exact wording on a dedicated compression model were not retrieved; the search summary found nothing on the compression model.

## 4. What output shapes make research directly usable by a downstream planning or debugging step? Any published templates?

### Takeaway
Published, reusable templates exist for decisions (MADR), for research findings with sources (Open Deep Research's compression format and its summary-plus-key-excerpts schema), and for separating verified facts from guesses (Magentic-One's fact sheet). I found no published standard for claim / source / confidence triples; that shape has to be assembled from these parts.

### Cited Findings

**Decision record: MADR (Markdown Architectural Decision Records)**
- [opened] Full template sections, in order: optional front matter (`status`, `date`, `decision-makers`, `consulted`, `informed`); title "representative of solved problem and found solution"; "Context and Problem Statement"; "Decision Drivers" (optional); "Considered Options"; "Decision Outcome"; "Consequences" (optional); "Confirmation" (optional); "Pros and Cons of the Options" (optional); "More Information" (optional). — [MADR adr-template.md](https://github.com/adr/madr/blob/develop/template/adr-template.md)
- [opened] The outcome line has a fixed form: `Chosen option: "{title of option 1}", because {justification. e.g., only option, which meets k.o. criterion decision driver | which resolves force {force} | … | comes out best (see below)}.` — [MADR adr-template.md](https://github.com/adr/madr/blob/develop/template/adr-template.md)
- [opened] Options and consequences use a fixed bullet grammar: "Good, because {argument a}", "Neutral, because {argument c}", "Bad, because {argument d}". — [MADR adr-template.md](https://github.com/adr/madr/blob/develop/template/adr-template.md)
- [opened] "Confirmation" asks how compliance will be checked: "Describe how the implementation / compliance of the ADR can/will be confirmed. Is there any automated or manual fitness function?" — [MADR adr-template.md](https://github.com/adr/madr/blob/develop/template/adr-template.md)
- [opened] "More Information" is the template's slot for evidence and confidence: "You might want to provide additional evidence/confidence for the decision outcome here ... and if/when it should be re-visited." — [MADR adr-template.md](https://github.com/adr/madr/blob/develop/template/adr-template.md)
- [opened] A minimal variant keeps only four parts: Context and Problem Statement, Considered Options, Decision Outcome, Consequences. — [MADR adr-template-minimal.md](https://github.com/adr/madr/blob/develop/template/adr-template-minimal.md)

**Research findings with sources: Open Deep Research**
- [opened] Researcher output format, three fixed parts: "**List of Queries and Tool Calls Made**", "**Fully Comprehensive Findings**", "**List of All Relevant Sources (with citations in the report)**". — [open_deep_research prompts.py](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/prompts.py)
- [opened] Citation rules: "Assign each unique URL a single citation number in your text", a closing "### Sources" list, numbered "sequentially without gaps", in the form "[1] Source Title: URL". It also allows agreement to be merged: "if three sources all say "X", you could say "These three sources all stated X"." — [open_deep_research prompts.py](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/prompts.py)
- [opened] Per-page schema used when a fetched web page is condensed: a `Summary` model with two fields, `summary` and `key_excerpts`. The verbatim excerpts travel with the summary. — [open_deep_research state.py](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/state.py)
- [opened] Delegation brief rules (the downward half of the handoff): "provide complete standalone instructions - sub-agents can't see other agents' work" and "Do NOT use acronyms or abbreviations in your research questions, be very clear and specific". — [open_deep_research prompts.py](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/prompts.py)
- [opened] The final report prompt picks structure by question type: comparison (intro, A, B, comparison, conclusion), list (a single list or table, "you don't need an introduction or conclusion"), overview (overview, concepts, conclusion), or a single-section answer. — [open_deep_research prompts.py](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/prompts.py)

**Epistemic status: Magentic-One fact sheet**
- [opened] Fixed headings: "1. GIVEN OR VERIFIED FACTS", "2. FACTS TO LOOK UP", "3. FACTS TO DERIVE", "4. EDUCATED GUESSES", with the rule "DO NOT include any other headings or sections in your response." The update prompt moves items between headings as evidence arrives: "moving educated guesses to verified facts if appropriate". — [autogen _magentic_one/_prompts.py](https://github.com/microsoft/autogen/blob/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_prompts.py)
- [opened] The progress ledger pairs every answer with its reason (`{"reason": string, "answer": boolean}`), a claim-plus-justification shape that code can parse. — [autogen _magentic_one/_prompts.py](https://github.com/microsoft/autogen/blob/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_prompts.py)

**Format for machine readers**
- [opened] 12-factor agents argues the consuming model need not get a message transcript: "you can build your own context format that's optimized for your use case", with listed benefits "Information Density: Structure information in ways that maximize the LLM's understanding" and "Token Efficiency". Its example uses XML-style tagged blocks. — [12-factor-agents factor 3](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-03-own-your-context-window.md)
- [opened] Claude Code's guidance for a downstream build step is a file, not a chat message: "Once `SPEC.md` exists, start a fresh session to build from it, so the build begins with a clean context and a written definition of done." — [Claude Code docs, best practices](https://code.claude.com/docs/en/best-practices.md)

### Inferences
- The deep-research skill that governed this pass (a local skill file, not a published template) already uses a claim-source shape per question: a 1-2 sentence takeaway, cited findings with one inline source each, inferences kept separate, and gaps, with the rule that an unsourced claim moves to gaps. It is a working example of the split recommended below.
- A composite shape covers what a planning step needs, each part borrowed from a published template:
  1. Answer first: one or two sentences (the "Takeaway").
  2. Recommendation in MADR's outcome grammar: chosen option, "because", and the decision drivers it satisfies.
  3. Alternatives with "Good, because / Bad, because" bullets, including why each was not chosen.
  4. Evidence table: claim, source URL, verbatim excerpt (Open Deep Research's `key_excerpts`), and status (Magentic-One's verified / to look up / derived / guess can serve as a four-level confidence scale).
  5. Gaps and conflicts, as their own section.
  6. Confirmation: how the planner can check the recommendation (MADR's fitness-function slot).
- For a debugging step the same evidence table works with different columns: hypothesis, evidence for, evidence against, how to test. I found no published template for this; it is an adaptation.
- Splitting "cited findings" from "inferences" matters more for an agent reader than for a human one, because a downstream model will otherwise treat every sentence as equally established (MAST 3.2 / 3.3).
- Keeping a verbatim excerpt beside each claim is the cheapest guard against commission errors (a summary that distorts its source), since the lead or a checker can compare claim and excerpt without re-fetching.
- Structure should follow the question type, as Open Deep Research does: a comparison gets a table, a list gets a list, a single fact gets one section. A fixed heavy template for every question adds tokens with no gain.

### Gaps
- I found no published template or standard for claim / source / confidence triples aimed at agent-to-agent use, and no study comparing output shapes (table versus prose versus JSON) by downstream task success.
- Evidence-table conventions from systematic reviews (for example GRADE or PRISMA) were not researched; relevant hosts were not reachable and they target human reviewers.
- The original Nygard ADR format and the Y-statement format were not opened (adr.github.io unreachable); only MADR was read.
- OpenAI Cookbook examples of structured research handoffs were not located; the cookbook repository was cloned but not searched in depth.

## 5. In Claude Code specifically: what do the official docs say about subagent context isolation, returning results, cost, and running subagents in parallel?

### Takeaway
A Claude Code subagent starts with a fresh context, sees only the delegation message Claude writes plus project files such as CLAUDE.md, and hands back a summary; its transcript stays on disk. It bills against the same usage as the main conversation, runs in the background by default, and can run in parallel (20 concurrent by default), with the docs warning that many detailed returns fill the lead's context.

All quotes below were checked against the downloaded Markdown of each page (retrieved 2026-11-16).

### Cited Findings

**Context isolation**
- [opened] "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task, and the subagent works from there. The exception is a fork, which inherits the parent conversation instead of starting fresh." — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] A subagent's system prompt is "the agent's own prompt plus environment details that Claude Code appends, not the Claude Code system prompt." Its startup context also includes CLAUDE.md files, git status and preloaded skills; "Explore and Plan start without your CLAUDE.md files and the git status snapshot to keep research fast and inexpensive." — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] Skills that run in a subagent have the same isolation: with `context: fork`, "The subagent doesn't see your conversation history, so the skill's instructions have to stand on their own." A warning adds that this is not a fork of the conversation: "When the task depends on that history, fork the conversation instead of using `context: fork`." — [Claude Code docs, skills](https://code.claude.com/docs/en/skills.md)
- [opened] A skill frontmatter can set `context: fork`, `agent` ("Which subagent type to use when `context: fork` is set") and `background` ("Set to `false` to wait for the forked subagent's result in the turn that invoked the skill"; default `true`). — [Claude Code docs, skills](https://code.claude.com/docs/en/skills.md)

**Returning results**
- [opened] "the subagent does that work in its own context and returns only the summary." Also: "the verbose output stays in the subagent's context while only the relevant summary returns to your main conversation." — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] Use a subagent when "The task produces verbose output you don't need in your main context", "You want to enforce specific tool restrictions or permissions", or "The work is self-contained and can return a summary". — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] Use the main conversation when "The task needs frequent back-and-forth or iterative refinement" or when "Latency matters. A subagent that isn't a fork starts fresh and may need time to gather context." — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] The full record survives outside the lead's context: transcripts are stored at `~/.claude/projects/{project}/{sessionId}/subagents/` as `agent-{agentId}.jsonl`; "when the main conversation compacts, subagent transcripts are unaffected"; they are deleted "after the `cleanupPeriodDays` retention period, 30 days by default". — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] A background subagent's result arrives later: with `context: fork`, "you keep working while it runs, and its result arrives in your conversation when it completes." — [Claude Code docs, skills](https://code.claude.com/docs/en/skills.md)
- [opened] In the pages read, a structured return is documented only for dynamic workflows: "If you pass a `schema` on an `agent()` call, that subagent returns JSON matching the shape instead of prose." The subagent frontmatter table (name, description, tools, disallowedTools, model, permissionMode, maxTurns, skills, mcpServers, hooks, memory, background, omitClaudeMd, effort, isolation, autoCompactWindow, color, initialPrompt, experimental) lists no output-schema field. — [Claude Code docs, workflows](https://code.claude.com/docs/en/workflows.md); [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)

**Cost**
- [opened] "What they cost you is mostly tokens, since every subagent sends its own requests and they count against the same usage as your main conversation. Sometimes it's time as well: a fresh subagent first has to gather context your conversation already had, so it can end up *slower* than doing the task where you are." — [Claude Code docs, best practices](https://code.claude.com/docs/en/best-practices.md)
- [opened] "Running many subagents that each return detailed results can consume significant context, and each subagent spends tokens of its own while it runs." — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] "The subagent's own requests still draw on your usage. To spend less on them, choose a smaller model for a subagent or run every subagent on one model." and "For simple subagent tasks, specify `model: haiku` in your subagent configuration." — [Claude Code docs, costs](https://code.claude.com/docs/en/costs.md)
- [opened] The only stated multiplier is for agent teams, not subagents: "Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode, because each teammate maintains its own context window and runs as a separate Claude instance." The comparison table rates token cost "Lower: results summarized back to main context" for subagents and "Higher: each teammate is a separate Claude instance" for teams. — [Claude Code docs, costs](https://code.claude.com/docs/en/costs.md); [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams.md)
- [opened] Subagent prompt cache lasts five minutes by default: "Subagents get five minutes unless you change it." — [Claude Code docs, best practices](https://code.claude.com/docs/en/best-practices.md)
- [opened] Workflows: "A workflow spawns many agents, so a single run can use meaningfully more tokens than working through the same task in conversation." A `Large workflow` warning appears "When a workflow schedules more than 25 agents, or its projected token total passes 1.5 million". — [Claude Code docs, workflows](https://code.claude.com/docs/en/workflows.md)
- [opened] Baseline for scale: "the average cost is around $13 per developer per active day and $150-250 per developer per month". — [Claude Code docs, costs](https://code.claude.com/docs/en/costs.md)

**Parallel and background execution**
- [opened] Parallel research is a documented pattern: "Each subagent explores its area independently, then Claude synthesizes the findings. This works best when the research paths don't depend on each other." — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] "With nothing configured, a subagent that Claude spawns from your main conversation starts in the background." Background subagents "run with a smaller built-in tool set than foreground subagents" — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] Concurrency limit: "By default, when 20 subagents are running in a session, spawning another with the Agent tool fails with `Concurrent subagent limit reached`", changeable with `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`. — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] Nesting: "By default, a subagent can spawn subagents of its own, up to three layers below the main conversation." At the limit a subagent "does its delegated work itself and returns one summary." In an interactive session "only the top-level subagent's summary returns to you". `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` turns nesting off. — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] For work that outgrows one context: "For work that needs to keep running in parallel or won't fit in one context window, run it in separate sessions and let Claude pass findings between them." — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] The built-in Explore and Plan agents "are one-shot and return no agent ID, so Claude can't resume them. Use `general-purpose` or a custom subagent when you need to continue the work." — [Claude Code docs, subagents](https://code.claude.com/docs/en/sub-agents.md)
- [opened] Workflows default to "Up to 16 concurrent agents" and keep "the intermediate results" in script variables, "so Claude's context holds only the final answer." — [Claude Code docs, workflows](https://code.claude.com/docs/en/workflows.md)
- [opened] Agent teams are a separate, experimental feature, "disabled by default", and the docs steer simple cases away from them: "Use subagents when you need quick, focused workers that report back. Use agent teams when teammates need to share findings, challenge each other, and coordinate on their own." and "For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective." — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams.md)
- [opened] A fresh-context reviewer is a recommended use: `/code-review` "reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code." — [Claude Code docs, best practices](https://code.claude.com/docs/en/best-practices.md)

### Inferences
- In Claude Code the handoff contract is entirely in prompts and files. A plain subagent has no output schema, so a plugin that wants a stable return shape must (a) state the template in the delegation brief or the subagent definition, and (b) have the researcher write its notes to a file and return a short pointer. The docs' own warning about "detailed results" filling context supports the file-plus-pointer split.
- Because the subagent "doesn't see your conversation history", the delegation message is the single point where 1.1 (task specification) failures are created or prevented. Open Deep Research's brief rules (standalone, no acronyms, non-overlapping scope) transfer directly.
- Cost of a lead-plus-N-researchers run is roughly the lead's session plus N independent sessions that each rebuild context, with a five-minute cache. The docs give no multiplier for subagents; the 7x figure is for agent teams in plan mode and should not be quoted for subagents.
- For a small feature, the docs' own ordering applies: main conversation for narrow or iterative questions, one subagent when the reading would flood the context, parallel subagents only when "the research paths don't depend on each other".
- A skill with `context: fork` gives a research skill isolation for free, but it then cannot see the conversation, so the skill text must tell Claude what to pass in.
- This run is itself an example of the pattern: a spawned researcher with a written brief, a notes file as the durable record, and a short handback.

### Gaps
