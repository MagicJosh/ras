# Deep-research systems: process and report format (as of 2026-11-16)

Evidence grades used below, because network access was limited to GitHub raw files and web search summaries:

- **[repo]**: I read the file itself, fetched from the repo's `main`/`master` branch on 2026-11-16. Quotes are verbatim.
- **[snippet]**: web search summary only; the page itself could not be opened from this network. Treat wording as approximate.
- **[leak]**: unofficial, undated prompt dump in a third-party GitHub repo (`asgeirtj/system_prompts_leaks`). Not vendor documentation; may be outdated or inaccurate.

Short names: ODR = LangChain `open_deep_research`; GPTR = GPT Researcher.

## 1. Stages, plan approval, and stopping rule per system

### Takeaway
Every system runs the same skeleton: scope the question, turn it into a written brief or plan, search and read in a loop with reflection, then write once at the end. They differ on who approves the plan: ChatGPT and the Gemini app show an editable plan (search snippets only, pages not opened); the APIs and the open-source tools default to no approval (read in repos). Stopping, where I could read it, is a hard budget (iterations, tool calls, depth, turns) plus a soft "stop when you can answer" instruction. The only explicit sufficiency test I found is in ODR's legacy workflow: an LLM grader returns `pass` or `fail` per section and supplies follow-up queries. How the three commercial products decide to stop is not documented in anything I could open.

**OpenAI deep research**

- ChatGPT asks clarifying questions through an intermediate model before research starts: "ChatGPT uses an intermediate model (like gpt-4.1) to help clarify your intent and gather more context (such as your preferences, goals, or constraints) before the research process begins." [repo] — [OpenAI cookbook, intro notebook](https://raw.githubusercontent.com/openai/openai-cookbook/main/examples/deep_research_api/introduction_to_deep_research_api.ipynb)
- The API has no clarify stage: "the Deep Research API skips this clarification step ... the model expects fully-formed prompts up front and will not ask for additional context or fill in missing information; it simply starts researching based on the input it receives." [repo] — [OpenAI cookbook, intro notebook](https://raw.githubusercontent.com/openai/openai-cookbook/main/examples/deep_research_api/introduction_to_deep_research_api.ipynb)
- OpenAI's sample pipeline for API users puts a triage agent in front, which hands off to a clarifying agent ("Ask 2–3 clarifying questions") or straight to an instruction-builder agent that rewrites the query into detailed research instructions; the research agent runs last. [repo] — [OpenAI cookbook, agents notebook](https://raw.githubusercontent.com/openai/openai-cookbook/main/examples/deep_research_api/introduction_to_deep_research_api_agents.ipynb)
- In the API the model "autonomously plans sub-questions, uses tools like web search and code execution, and produces a final structured response"; intermediate steps are exposed as `reasoning`, `web_search_call`, `code_interpreter_call` and `mcp_call` items. [repo] — [OpenAI cookbook, intro notebook](https://raw.githubusercontent.com/openai/openai-cookbook/main/examples/deep_research_api/introduction_to_deep_research_api.ipynb)
- ChatGPT proposes a research plan the user can edit before the run, shows progress in real time, and lets the user interrupt to change focus or sources. [snippet] — [OpenAI Help Center, Deep research FAQ](https://help.openai.com/en/articles/10500283-deep-research-faq)
- A leaked ChatGPT prompt shows the kickoff as two tool methods, `clarify_with_text` and `start_research_task`: "If you require additional information from the user before starting the task, ask them for more detail before starting research using clarify_with_text." [leak] — [system_prompts_leaks, OpenAI/tool-deep-research.md](https://raw.githubusercontent.com/asgeirtj/system_prompts_leaks/main/OpenAI/tool-deep-research.md)

**Google Gemini Deep Research**

- The agent "autonomously plans, executes, and synthesizes multi-step research tasks into detailed, cited reports ... searching the web, reading pages, executing code, and analyzing documents"; it "can consult over 100 sources in a single task" and runs in the background for "several minutes". [repo] — [google-gemini/cookbook, Get_started_Deep_Research.ipynb](https://raw.githubusercontent.com/google-gemini/cookbook/main/quickstarts/Get_started_Deep_Research.ipynb)
- API plan approval is opt-in, in three steps: request a plan with `collaborative_planning=True` ("The agent returns a research plan instead of a full report"), refine it over turns with `previous_interaction_id`, then approve by setting `collaborative_planning=False`. "Simply sending 'go ahead' without flipping the flag will not trigger report generation." The default is `false`. [repo] — [google-gemini/cookbook, Get_started_Deep_Research.ipynb](https://raw.githubusercontent.com/google-gemini/cookbook/main/quickstarts/Get_started_Deep_Research.ipynb)
- Two agent versions exist: `deep-research-preview-04-2026` (speed) and `deep-research-max-preview-04-2026` ("maximum search exhaustiveness and report comprehensiveness"). [repo] — [google-gemini/cookbook, Get_started_Deep_Research.ipynb](https://raw.githubusercontent.com/google-gemini/cookbook/main/quickstarts/Get_started_Deep_Research.ipynb)
- Follow-up questions after a report go to a standard Gemini model, not the research agent, so they do not rerun the research. [repo] — [google-gemini/cookbook, Get_started_Deep_Research.ipynb](https://raw.githubusercontent.com/google-gemini/cookbook/main/quickstarts/Get_started_Deep_Research.ipynb)
- In the Gemini app, Gemini creates a research plan, the user can click "Edit plan" to change it, then clicks "Start research". [snippet] — [Google Help, Use Deep Research in Gemini Apps](https://support.google.com/gemini/answer/15719111)

**Perplexity Deep Research**

- Perplexity's launch post describes an agent that "iteratively searches, reads documents, and reasons about what to do next, refining its research plan as it learns more", then synthesizes a report; a typical run does dozens of searches and reads hundreds of sources. [snippet] — [Perplexity blog, Introducing Perplexity Deep Research](https://www.perplexity.ai/hub/blog/introducing-perplexity-deep-research)
- The API model `sonar-deep-research` takes a `reasoning_effort` of low, medium or high; Perplexity does not expose the chain of thought for Deep Research. [snippet] — [Perplexity API reference](https://docs.perplexity.ai/api-reference/chat-completions-post); [Perplexity FAQ](https://docs.perplexity.ai/faq/faq)
- A leaked prompt gives explicit clarify criteria. Call `clarifying_questions` when: "Subjective terms present ('best', 'good', 'top')", "Personal decisions (purchases, investments, career, health)", "Undefined scope (budget, timeframe, experience level, region)", "Multiple valid interpretations exist". Skip when: "Single factual answer" or "Scope already specified". If the user skips the questions: "proceed directly using reasonable defaults. Do NOT re-ask questions in any form." [leak] — [system_prompts_leaks, Perplexity/deep-research.md](https://raw.githubusercontent.com/asgeirtj/system_prompts_leaks/main/Perplexity/deep-research.md)
- The same leak's loop instruction: "Decompose complex user queries into discrete tool calls for accuracy and parallelization. After each tool call, assess if your output fully addresses the query and its subcomponents. Continue until the user query is resolved." Search guidance: "Use short, simple, keyword-based search queries", up to 3 queries per call, split multi-entity queries into single-entity ones. [leak] — [system_prompts_leaks, Perplexity/deep-research.md](https://raw.githubusercontent.com/asgeirtj/system_prompts_leaks/main/Perplexity/deep-research.md)

**GPT Researcher**

- Standard mode, five steps: "Create a task-specific agent based on a research query. Generate questions that collectively form an objective opinion on the task. Use a crawler agent for gathering information for each question. Summarize and source-track each resource. Filter and aggregate summaries into a final research report." [repo] — [gpt-researcher README](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/README.md)
- The planner prompt is a fixed-count query generator: "Write {max_iterations} search queries to research the following task" (`MAX_ITERATIONS: 3` in the default config), plain natural language, no search operators. The prompt contains no sufficiency check; I did not read the orchestration code, so a check elsewhere is not ruled out. [repo] — [gpt_researcher/prompts.py](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/gpt_researcher/prompts.py); [config/variables/default.py](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/gpt_researcher/config/variables/default.py)
- Deep mode is a recursive tree: generate `breadth` queries each with a research goal, run them, extract "learnings" with source URLs plus follow-up questions, then recurse with `new_breadth = max(2, breadth // 2)` and `depth - 1` until depth runs out. Default depth is 2. [repo] — [gpt_researcher/skills/deep_research.py](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/gpt_researcher/skills/deep_research.py)
- Deep mode generates clarifying "follow-up questions" from an initial search but never asks the user: the answers are hard-coded to "Automatically proceeding with research". [repo] — [gpt_researcher/skills/deep_research.py](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/gpt_researcher/skills/deep_research.py)
- Deep-mode defaults differ by where you look. Default config: `DEEP_RESEARCH_BREADTH: 3`, `DEEP_RESEARCH_DEPTH: 2`, `DEEP_RESEARCH_CONCURRENCY: 4`. Docs say breadth 4, depth 2, concurrency 4. The `getattr` fallbacks in the skill are breadth 4, depth 2, concurrency 2, and apply only if the config lacks the key. Breadth is the real disagreement (3 in config, 4 in docs). [repo] — [config/variables/default.py](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/gpt_researcher/config/variables/default.py); [docs deep_research.md](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/docs/docs/gpt-researcher/gptr/deep_research.md); [deep_research.py](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/gpt_researcher/skills/deep_research.py)
- Multi-agent mode (inspired by STORM) has five stages: "Planning stage, Data collection and analysis, Review and revision, Writing and submission, Publication", with roles Human, Chief Editor, Researcher, Editor, Reviewer, Revisor, Writer, Publisher. Each outline section is researched, reviewed and revised in parallel. [repo] — [multi_agents/README.md](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/multi_agents/README.md)
- Plan approval in multi-agent mode is optional and off by default (`"include_human_feedback": false`). When on, the human is asked: "Any feedback on this plan of topics to research? {layout}? If not, please reply with 'no'." Feedback goes back to the editor: "You must plan the sections based on the human feedback." [repo] — [multi_agents/agents/human.py](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/multi_agents/agents/human.py); [agents/editor.py](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/multi_agents/agents/editor.py); [task.json](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/multi_agents/task.json)
- The review loop stops when the reviewer returns `None`: "If the draft meets all the guidelines, please return None." On later rounds: "Please provide additional feedback ONLY if critical since the reviser has already made changes based on your previous feedback." The reviewer runs only when the task sets `follow_guidelines`, which is `false` in the shipped `task.json`, so review is off by default. [repo] — [multi_agents/agents/reviewer.py](https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/multi_agents/agents/reviewer.py)

**STORM and Co-STORM**

- STORM has two stages: "Pre-writing stage: The system conducts Internet-based research to collect references and generates an outline. Writing stage: The system uses the outline and references to generate the full-length article with citations." [repo] — [storm README](https://raw.githubusercontent.com/stanford-oval/storm/main/README.md)
- STORM's research method is question asking, not query planning: "Perspective-Guided Question Asking" (personas found by surveying articles on similar topics) and "Simulated Conversation" between a Wikipedia writer and a topic expert grounded in search results. [repo] — [storm README](https://raw.githubusercontent.com/stanford-oval/storm/main/README.md)
- The persona prompt: "You need to select a group of Wikipedia editors who will work together to create a comprehensive article on the topic. Each of them represents a different perspective, role, or affiliation related to this topic." [repo] — [persona_generator.py](https://raw.githubusercontent.com/stanford-oval/storm/main/knowledge_storm/storm_wiki/modules/persona_generator.py)
- Stop rule for each conversation: the writer prompt says "When you have no more question to ask, say 'Thank you so much for your help!' to end the conversation", and the code also caps turns. Defaults: `max_conv_turn=3`, `max_perspective=3`, `max_search_queries_per_turn=3`, `search_top_k=3`. [repo] — [knowledge_curation.py](https://raw.githubusercontent.com/stanford-oval/storm/main/knowledge_storm/storm_wiki/modules/knowledge_curation.py); [storm_wiki/engine.py](https://raw.githubusercontent.com/stanford-oval/storm/main/knowledge_storm/storm_wiki/engine.py)
- The expert module's four steps: "1. Generate queries from the question. 2. Search for information using the queries. 3. Filter out unreliable sources. 4. Generate an answer using the retrieved information." [repo] — [knowledge_curation.py](https://raw.githubusercontent.com/stanford-oval/storm/main/knowledge_storm/storm_wiki/modules/knowledge_curation.py)
- The outline is made in two passes: a draft from the model's own knowledge, then "Improve an outline ... based on the information learned from an information-seeking conversation". [repo] — [outline_generation.py](https://raw.githubusercontent.com/stanford-oval/storm/main/knowledge_storm/storm_wiki/modules/outline_generation.py)
- Co-STORM is a turn-managed round table with three participant types: LLM experts (grounded answers or follow-up questions), a moderator, and the human user, who can "observe the discourse" or "actively engage in the conversation by injecting utterances to steer the discussion focus". [repo] — [storm README](https://raw.githubusercontent.com/stanford-oval/storm/main/README.md)
- The Co-STORM moderator exists "to inject new perspectives into the conversation to avoid stagnation, repetition, or overly niche discussions", by asking questions "based on unused, uncited snippets of information retrieved since the last moderator's turn". It takes over after 3 consecutive answering turns (`moderator_override_N_consecutive_answering_turn=3`). [repo] — [co_storm_agents.py](https://raw.githubusercontent.com/stanford-oval/storm/main/knowledge_storm/collaborative_storm/modules/co_storm_agents.py); [collaborative_storm/engine.py](https://raw.githubusercontent.com/stanford-oval/storm/main/knowledge_storm/collaborative_storm/engine.py)
- Co-STORM budgets: `total_conv_turn=20`, warm start with up to 3 experts and 2 turns each, 2 active round-table experts. Each expert turn is one of four typed moves: "Original Question", "Further Details", "Information Request", "Potential Answer". [repo] — [collaborative_storm/engine.py](https://raw.githubusercontent.com/stanford-oval/storm/main/knowledge_storm/collaborative_storm/engine.py); [costorm_expert_utterance_generator.py](https://raw.githubusercontent.com/stanford-oval/storm/main/knowledge_storm/collaborative_storm/modules/costorm_expert_utterance_generator.py)
- Co-STORM files every retrieved fact into a tree-shaped "mind map" as it goes (`insert`, `step: [child]`, `create: [new child]`); node expansion triggers when a node holds more than 10 snippets (`node_expansion_trigger_count=10`). The report is generated from that tree. [repo] — [information_insertion_module.py](https://raw.githubusercontent.com/stanford-oval/storm/main/knowledge_storm/collaborative_storm/modules/information_insertion_module.py); [collaborative_storm/engine.py](https://raw.githubusercontent.com/stanford-oval/storm/main/knowledge_storm/collaborative_storm/engine.py)

**LangChain open_deep_research (ODR)**

- Graph: `clarify_with_user` → `write_research_brief` → `research_supervisor` (which spawns `researcher` → `researcher_tools` → `compress_research` per sub-topic) → `final_report_generation`. [repo] — [deep_researcher.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/deep_researcher.py)
- Clarification is on by default (`allow_clarification=True`) and limited to one round: "If you can see in the messages history that you have already asked a clarifying question, you almost always do not need to ask another one. Only ask another question if ABSOLUTELY NECESSARY." Output is JSON with `need_clarification`, `question`, `verification`. If no question is needed, the verification message must "Briefly summarize the key aspects of what you understand from their request" and "Confirm that you will now begin the research process". [repo] — [prompts.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/prompts.py); [configuration.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/configuration.py)
- The plan is a research brief, not a plan shown for approval. The current graph goes straight from brief to research. The older workflow in `src/legacy/` is described as "Plan-and-Execute: Structured workflow with human-in-the-loop planning" and "less performant than the current implementation". [repo] — [open_deep_research README](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/README.md)
- Supervisor stop rule, verbatim: "Bias towards single agent - Use single agent for simplicity unless the user request has clear opportunity for parallelization"; "Stop when you can answer confidently - Don't keep delegating research for perfection"; "Always stop after {max_researcher_iterations} tool calls". Defaults: `max_researcher_iterations=6`, `max_concurrent_research_units=5`. The supervisor ends by calling a `ResearchComplete` tool. [repo] — [prompts.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/prompts.py); [configuration.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/configuration.py)
- Scaling rule, verbatim: "Simple fact-finding, lists, and rankings can use a single sub-agent"; "Comparisons presented in the user request can use a sub-agent for each element of the comparison". Delegation rule: "provide complete standalone instructions - sub-agents can't see other agents' work"; "Do NOT use acronyms or abbreviations in your research questions". [repo] — [prompts.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/prompts.py)
- Researcher stop rule, verbatim: "Simple queries: Use 2-3 search tool calls maximum. Complex queries: Use up to 5 search tool calls maximum. Always stop: After 5 search tool calls if you cannot find the right sources." and "Stop Immediately When: You can answer the user's question comprehensively; You have 3+ relevant examples/sources for the question; Your last 2 searches returned similar information". [repo] — [prompts.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/prompts.py)
- ODR pairs a prompt budget with a code backstop: the prompt says 5 search calls at most, and the code ends the researcher after `max_react_tool_calls=10` model turns (`tool_call_iterations` is incremented once per researcher model call). Since the prompt requires a `think_tool` turn after each search, 5 searches plus 5 reflections fit the cap of 10. [repo] — [prompts.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/prompts.py); [configuration.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/configuration.py); [deep_researcher.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/deep_researcher.py)
- Reflection is a mandatory separate step: "Use think_tool after each search to reflect on results and plan next steps", with four questions: "What key information did I find? What's missing? Do I have enough to answer the question comprehensively? Should I search more or provide my answer?" Search order: "Start with broader searches", then "Execute narrower searches as you gather information". [repo] — [prompts.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/open_deep_research/prompts.py)
- ODR's legacy workflow (kept in `src/legacy/`) is plan-first. The planner prompt: "Generate a list of sections for the report. Your plan should be tight and focused with NO overlapping sections or unnecessary filler." Each section has Name, Description, Research (true or false) and Content; "A report must have AT LEAST 2-3 sections with Research=True to be useful." The prompt has a `<Feedback>` block: "Here is feedback on the report structure from review (if any)". [repo] — [src/legacy/prompts.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/legacy/prompts.py)
- The legacy workflow has an explicit sufficiency test per section: "Evaluate whether the section content adequately addresses the section topic. If the section content does not adequately address the section topic, generate {number_of_follow_up_queries} follow-up search queries to gather missing information." Output schema: `grade: Literal["pass","fail"]` and `follow_up_queries`. The loop is capped by `max_search_depth: int = 2` ("Maximum number of reflection + search iterations") with `number_of_queries: int = 2` per iteration. [repo] — [src/legacy/prompts.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/legacy/prompts.py); [src/legacy/configuration.py](https://raw.githubusercontent.com/langchain-ai/open_deep_research/main/src/legacy/configuration.py)

### Inferences
- The stable stage list across all six is: clarify (optional, one round) → brief → search/read/reflect loop → compress findings with sources → write once. A small skill can copy this without multi-agent machinery; ODR itself says "Bias towards single agent".
- Plan approval is a product-surface feature (ChatGPT, Gemini app), not a property of the research engines. Both vendors' APIs default to no approval, and ODR moved human-in-the-loop planning to "legacy", calling it "less performant than the current implementation". For a CLI skill, a short "here is what I understood and will research" message (ODR's `verification`) is the cheap middle ground.
- The best public stopping rule is ODR's: a numeric cap plus three observable conditions (can answer, 3+ sources, last two searches repeated). ODR's legacy section grader (`pass`/`fail` plus follow-up queries, at most 2 rounds) is the only public example of a graded sufficiency check. The other systems I could read stop on budget alone.
- ODR's brief-writing prompt is near-verbatim the OpenAI cookbook rewriting prompt (same five headings: "Maximize Specificity and Detail", "Fill in Unstated But Necessary Dimensions as Open-Ended", "Avoid Unwarranted Assumptions", "Use the First Person", "Sources"). This text is effectively the public standard for turning a request into a research brief.

### Gaps
- How ChatGPT, the Gemini app and Perplexity decide to stop is not documented in anything I could open. The Perplexity leak only says "Continue until the user query is resolved".
- The Perplexity leak lists a `research` skill and a `research-report` skill by description only; their bodies (the actual methodology and report instructions) are not in the file.
- Whether Co-STORM enforces `total_conv_turn` or leaves it to the caller was not checked in code.
- Tried and failed (proxy returned 403 or the host did not resolve): `arxiv.org`, `ar5iv.labs.arxiv.org`, `aclanthology.org`, `openreview.net`, `developers.openai.com`, `platform.openai.com`, `help.openai.com`, `ai.google.dev`, `www.perplexity.ai`, `docs.perplexity.ai`. Only `raw.githubusercontent.com` and web search worked. The STORM and Co-STORM papers were therefore not read.
- Not attempted after the pattern was clear; known from search snippets only: `support.google.com`, `storm-project.stanford.edu`. Not attempted and not used: `docs.gptr.dev`, `blog.langchain.com`, `cookbook.openai.com` (the repo copies were read instead).
- Not read in the repos: GPT Researcher's orchestration code outside the prompt file and the deep-research skill; the multi-agent `researcher.py`, `reviser.py`, `orchestrator.py`; Co-STORM's expert-generation module; ODR's legacy graph code.

## 2. Report shape: section order, where the answer sits, citations, source lists and dates

### Takeaway
Among the prompts I could read, only the leaked (unofficial) Perplexity prompt puts the answer first ("Begin with a direct 1-2 sentence answer"). The open-source systems put it in an introduction or leave structure to the model, and ODR explicitly lets the report shape follow the question type. Citations are inline everywhere; the split is between numbered `[n]` with a Sources list at the end (ODR, STORM) and inline links with no list (Perplexity, OpenAI annotations). Only GPT Researcher asks for dates in the source list, through APA format. Real ChatGPT, Gemini and Perplexity reports were not seen.

### Cited Findings

| System | Section order | Direct answer position | Inline citation form | Source list | Dates on sources |
|---|---|---|---|---|---|
| OpenAI | Free; `#`/`##`/`###`, short paragraphs [leak] | Not specified | Character-span annotations with title and URL | Built by the caller from annotations | No |
| Gemini | Free; steerable by prompt (example: Executive Summary first) | Not specified | "cited reports" (format not seen) | Not seen | Not seen |

### Inferences
- "Answer first" is not the norm in public prompts. Only the Perplexity leak demands it; ODR allows it ("1/ answer") but does not require it. A skill that wants bottom-line-first has to say so explicitly.
- ODR's "shape follows question type" list (comparison, list, overview, single answer) is the most reusable template: four short patterns instead of one rigid outline. ODR moved from a fixed template with word limits (legacy) to this looser form (current).
- ODR legacy's `<Final Check>` (every claim grounded, each URL once, numbering without gaps) is the only public self-check list for citations in this set.
- Two citation styles are in use and they do not mix: per-sentence inline links with no list (Perplexity, OpenAI) and numbered references with a list (ODR, STORM, GPTR). ODR's own prompt asks for both `[Title](URL)` and numbered `[1]`, which is inconsistent; a skill should pick one.
- No prompt I read asks for a retrieval date or publication date per source except GPTR's APA format. If dated sources matter, the skill must ask for them; nothing in these prompts gives it for free.
- Intermediate notes are kept verbatim and source-complete (ODR compress step, STORM information table, Co-STORM mind map); only the final writer condenses.

### Gaps
- No verbatim example of a finished ChatGPT, Gemini or Perplexity report was reachable, so their real section order and source-list layout are known only through prompts, API docs and search snippets.
- How Gemini attaches citations in the report text (annotation format) was not visible in the cookbook; the API docs page could not be opened.
- Whether the Perplexity `research-report` skill uses a source list is unknown; its body is not in the leak.

## 3. Confidence, uncertainty, conflicting sources and unknowns

### Takeaway
No prompt, config or doc I could read defines an explicit confidence scale or tells the writer how to present conflicting sources. That covers the three open-source systems fully enough to state it; for ChatGPT, Gemini and Perplexity it covers only cookbook notebooks, search snippets and unofficial leaks, so it is "none found", not "none exists". What exists is narrower: source-quality preferences, "say what you could not find" rules in STORM, Co-STORM and the Perplexity leak, and "do not invent details, state that they are unspecified" in the OpenAI and ODR brief prompts. GPT Researcher pushes the other way and requires a firm opinion.

### Cited Findings
- A text search for `confiden`, `uncertain`, `conflict`, `contradict`, `discrepan`, `limitation`, `gaps`, `bias`, `reliab`, `trust`, `controvers` across the downloaded files (ODR current prompts, GPTR prompts, STORM and Co-STORM modules, both cookbooks, both leaks; ODR legacy prompts were read but not included in the search) found no confidence scale and no conflict-handling instruction. The only "confidence" wording is the stop rule "Stop when you can answer confidently". ### Inferences
- An explicit confidence scale, a "conflicting sources" rule and an "unknowns" section would be additions beyond what these systems publish, not a copy of common practice.
- The closest thing to a graded judgment in this set is ODR legacy's binary section grade (`pass`/`fail`), which grades coverage of the section topic, not confidence in claims.
- The nearest reusable wording is STORM's: answer only from gathered information, and when it does not cover the question say so and "explain any limitations or gaps".
- There is a real design tension to settle: GPT Researcher forces a "concrete and valid opinion", while STORM and Perplexity force restraint. A skill can have both by separating a committed answer from a stated list of what is unverified.
- Systems push the verification burden to the reader (citations as the trust mechanism, "check the sources") instead of grading their own claims.

### Gaps
- I could not confirm whether Google's Gemini Deep Research docs advise how to handle missing data in the prompt; a targeted search found nothing and the page could not be opened.
- The STORM and Co-STORM papers' evaluation numbers (citation recall and precision, and the 25% and 10% improvements a search summary attributes to the paper) were not verified against the paper.
- The Perplexity `research` skill's cross-validation method is unknown.
- I found no reliable source showing that any of these products computes or displays a per-claim confidence score.

### Inferences
- For a small skill, the three most copyable texts are: OpenAI's clarifying guidelines (ask only what would "change the structure, depth, or direction of the answer"; 3 to 6 questions, or ODR's stricter one round), the shared OpenAI/ODR brief guidelines, and ODR's researcher block (`<Hard Limits>` plus `<Show Your Thinking>`).
- The Perplexity leak, if accurate, shows a vendor splitting "how to research" and "how to write the report" into two separate skills, which matches the split between ODR's researcher and final-report prompts.
- Prompt weight sits in three places in every public set: the brief, the stop rules, and the citation rules. Report-structure instructions are short and permissive by comparison.
